## Google identity & roles — real OAuth (Google Identity Services)
- `do what is required with oauth to use google` (verbatim follow-up; this section records what was implemented)
- Real Google sign-in is implemented with Google Identity Services (GIS), Google's OAuth 2.0 / OpenID Connect flow for websites, per Google's official guides:
  - Button and client setup: https://developers.google.com/identity/gsi/web/guides/display-button and the JS reference https://developers.google.com/identity/gsi/web/reference/js-reference — the client loads Google's library from https://accounts.google.com/gsi/client (script URL as given in Google's guide), calls `google.accounts.id.initialize({ client_id, callback })` and `renderButton`; after the user picks an account and consents, Google returns a signed ID token (JWT) to the callback.
  - Server verification: https://developers.google.com/identity/sign-in/web/backend-auth — the `verifyGoogleCredential` action verifies the token server-side: RS256 signature checked against Google's public keys from https://www.googleapis.com/oauth2/v3/certs (the JWK URL linked from that guide; keys cached per its Cache-Control max-age and refetched once on an unknown kid for key rotation), plus the guide's claim checks — `iss` is accounts.google.com, `aud` equals this app's client ID, `exp` has not passed, `email_verified` is true. Only infrastructure failures (key fetch / crypto support) fall back to Google's tokeninfo endpoint https://oauth2.googleapis.com/tokeninfo (URL from the same guide, which performs the same checks on Google's side); signature/claim failures never fall back. Only the verified `sub` (Google ID), `email`, and `name` are ever trusted as identity — client-supplied identity claims are no longer accepted anywhere in the sign-in path.
- The OAuth client ID is the one artifact only the Google account owner can create (Google Cloud Console: OAuth consent screen + a "Web application" client ID + this app's origin registered as an Authorized JavaScript origin), so it lives in the database: `app_settings` key `google_client_id` (migration 0006), managed in-app via Admin Review → "Google sign-in connection" (`setGoogleClientId`, admin-gated, format-validated; `getGoogleConfig` exposes it to the client — client IDs are public identifiers that ship in the page, and the GIS ID-token flow needs no client secret). The sign-in dialog and the admin panel both show the exact step-by-step setup, including the app's current origin to register in the Cloud Console.
- Until a client ID is saved, real sign-in cannot start, so the sign-in dialog keeps the earlier account chooser as a clearly labeled simulated prototype fallback (demo accounts + custom identity) next to the connection steps; the moment a client ID exists, the dialog shows only Google's real sign-in button and the simulation disappears. This keeps the prototype demoable before the owner's one-time Cloud Console step is done.
- Placeholder reconciliation: after a verified sign-in, `verifyGoogleCredential` replaces the stored Google ID on any admin/gatekeeper row whose email matches the verified email but whose Google ID is a placeholder, anchoring it to the real `sub` (this is how jpgelber@gmail.com, added earlier by email with a placeholder ID, becomes tied to the real Google ID at first sign-in). Role checks continue to match by Google ID or email.
- Storage: `registrations.google_id` + `auth_provider` (google|manual); `authorized_admins` (google_id unique, email, display_name) seeded once with two demo admins (admin@cbict.org / google-demo-admin-001, jonathan@cbict.org / google-jonathan-demo); `authorized_gatekeepers` (same shape) seeded once with one demo gatekeeper (door@cbict.org / google-demo-gatekeeper-001). Admins add/remove both lists in the admin portal; server actions re-check the requester's Google ID against the approvers list for admin mutations and gatekeeper-list changes.
- Role check: `checkAdminAccess(googleId, email)` returns isAdmin / isGatekeeper / role; the client renders the Admin Review + Door Check-In tabs only when isAdmin is true, the Gatekeeper Check tab only when isGatekeeper is true (and not admin), and otherwise only Register + My Pass/My Events. Signed-in attendees get `lookupMyRegistrations(googleId, email)` showing their events, codes, and QR passes.
- Revoke: `revokeAttendance` sets status `revoked`, clears `code` and `checkedInAt` — the old code then returns not-found from `verifyCode`, which now also returns the attendee's email, phone, and event location for the gatekeeper/door result card.

## Calendar invite
- Generated client-side as a downloadable .ics file from the approval email preview and from the pass in My Pass; no server state. The invite carries the event title, date, parsed start/end clock times from the event's time text (all-day when the text has no clock time, e.g. "Evening"), location, the pass code in the description, and the QR pass graphic embedded as a base64 PNG ATTACH (rendered from the same deterministic pattern as the on-screen pass). Calendar clients that ignore ICS attachments still show the pass code in the entry notes.

## CAPTCHA for manual (non-Google) registrations
- `If someone registered without Google we need a captcha to validate human` (verbatim follow-up; defines this section)
- Manual registrations (no Google ID) must solve a server-generated CAPTCHA; Google registrations skip it because Google's verified ID token already establishes identity.
- Implementation is self-hosted (no external CAPTCHA provider / no site keys to configure): `getCaptchaChallenge` generates a random 5-character code from an unambiguous alphabet, renders it as a distorted SVG (per-character rotation/size/color variation, interference lines and dots), stores only `{ id, answer, expiresAt, createdAt }` in the new `captcha_challenges` table (migration 0007) with a 10-minute expiry, and returns `{ challengeId, svg }` — the answer never leaves the server. `register` requires `captchaId` + `captchaAnswer` whenever the registration is not a Google one, looks the challenge up, deletes it on first presentation (single-use, success or failure), and rejects on missing / expired / already-used / mismatched answers with a message that prompts the client to show a fresh image. The client shows the CAPTCHA block only when the form is not being submitted as a Google registration, offers a "New image" refresh, clears and refetches after any CAPTCHA error, and disables submit while the image loads. Expired rows are opportunistically deleted when new challenges are created.

## Long-term data behavior
- **Refresh policy**: No scheduled refresh; all data is user-entered at runtime (registrations, admin decisions, check-ins) plus the one-time demo event seed.
- **Growth**: Events and registrations tables grow as the user demos; admin list supports filtering by event and status.
- **Ordering**: Events by date ascending; registrations newest first in admin, grouped/filterable by status.
- **Time semantics**: Event date/time stored as plain local date + time strings as displayed on cbict.org (America/New_York congregation); registration/check-in timestamps stored as instants and rendered viewer-local.

## Rejected approaches
- **Tried**: Real camera-decoded QR generation via a bundled QR library
  **Why rejected (at the time)**: No QR library existed in the workspace dependency set and adding one was unverified; the prototype instead issued a QR-style pass graphic carrying a unique human-readable credential code (e.g. CBI-7K2QX9), with door check-in by code entry, guest-list tap, and the browser BarcodeDetector API when available.

- **Tried**: Sending real approval emails
  **Why rejected**: No mail connector is in scope for this prototype; approving a registration generates the exact approval email (with event date/time reiterated and the pass code) as an in-app preview marked as the automated email, so the demo shows precisely what the attendee would receive.

## Mobile-first app + phone camera QR scanning (gatekeeper & admin)
- `Can we have a mobile version for the gatekeeper who can use their phone to scan the QR code?` (verbatim follow-up; defines this section)
- `build the whole app for mobile — make the entire app mobile-first and responsive so it works well on phones, and enable camera use for both admin and gatekeeper (camera QR scanning for check-in, usable by admins and gatekeepers on their phones)` (parent-relayed follow-up; widens this section to the whole app and both door roles)
- **Real QR codes**: the previous pass graphic was a decorative QR-style pattern no camera could decode. Passes (My Pass / My Events, admin email preview, and the .ics attachment image) are now genuine QR codes generated with the `qrcode` npm package (added via `bun add qrcode jsqr @types/qrcode`), encoding the pass code text itself (e.g. `CBI-7K2QX9`) — so the in-app scanner and any phone's built-in camera can read them.
- **Camera scanning**: the old scanner used the browser BarcodeDetector API, which does not exist on iPhone Safari. Scanning now decodes the camera stream in-page with `jsQR`, which works on iPhone and Android. A shared `useScanner` hook (getUserMedia with `facingMode: "environment"`, requestAnimationFrame frame decode, single-result stop) plus a shared `ScannerControls` component (large full-width scan button, live video with a framing guide, big stop button) serve both the Gatekeeper Check tab and the admin Door Check-In tab. Scanned text is normalized by `extractPassCode` (pulls the `XXX-XXXXXX`-style code out of any longer payload) and sent to the unchanged `verifyCode` action; manual code entry remains as the fallback, and camera-denied / non-HTTPS cases explain that the typed code works the same.
- **Mobile-first pass over the whole app**: header shrinks on small screens, the tab bar becomes a single row of ≥44px touch targets that stretch across the phone width, main content uses tighter phone padding plus safe-area bottom padding, the gatekeeper screen leads with the scan button and a "Scan next pass" loop (gatekeepers also land directly on their check screen after sign-in), check-in buttons in the result card and guest list are ≥44–48px tall, and code inputs use `autoCapitalize="characters"` for phone keyboards. Desktop keeps the wider composed layout via `sm:` breakpoints.

## Approvals by email (per-event approver addresses)
- `Can we have approvals processed through email? we can associate each event to an approval email(s). The interface can approve, but the approver can approve through the email` (verbatim follow-up; defines this section)
- **Per-event approvers**: `events.approval_emails` (migration 0008) stores a JSON array of email addresses per event, edited in the admin event form ("Approval emails", one per line or comma-separated) and shown on each event row in Admin Review. When an event has none, approval requests fall back to the authorized administrators' email addresses.
- **Approval requests**: `register` creates one `approval_requests` row per approver (migration 0008) carrying a unique random token (`apr-<48 hex>`) with a 7-day expiry. The row represents the approval-request email: its recipient, subject ("Approval requested — <name> registered for <event>"), full body with attendee + event details, and Approve / Not approved links. Links are `<app URL>?approval=<token>&decision=approved|denied`.
- **Deciding from the email**: the token is the credential — no sign-in needed. The App shell checks the URL for `approval`/`decision` params on load, calls `decideByEmailToken`, shows the outcome ("Approval from your email" card), and strips the token from the address. The same action powers the preview buttons. First decision wins: deciding marks every token for the registration used (`usedAt`), the deciding token also records the `decision`, and later clicks return `already_decided` with the current status. Expired links return `expired`; replaced/unknown tokens return `invalid`. `registrations.decided_via` records the source ("Admin review" vs "Email link · <approver email>") and shows on the admin registration card.
- **Interface parity**: interface approve/deny/revoke (`setApproval` / `revokeAttendance`) share `applyApprovalDecision` with the email path and retire outstanding email links, so the two channels can't double-decide. Admins can preview each approval email from a pending registration ("Approval request email" button) and resend (`resendApprovalRequests` — fresh tokens; links in earlier emails stop working; also the way to create requests for registrations that predate this feature). `listApprovalRequests` is admin-gated (requester must be an authorized administrator) because the tokens are live credentials. The registration success screen names the approver addresses the request went to.
- **Prototype honesty (unchanged mail posture)**: consistent with the rejected real-email approach above, no real email leaves the app — the approval email is rendered exactly as it would be sent, as an in-app preview labeled as such, with its real token links live. Wiring real SMTP/provider sending later only changes delivery, not the token/decision mechanics.

## PII encryption at rest + tenant isolation (security)
- Follow-up spec (parent-relayed): organizations' data strictly separated; sensitive attendee data (names, emails, phone numbers, question answers) encrypted so a copy of the stored data alone cannot be read, with keys kept separate from the data.
- **Encryption**: AES-256-GCM per value (random IV, `enc:v1:` prefix) implemented in `server/src/privileged.ts`. The 32-byte key lives in a key file at `~/.config/cbi-event-registration/pii-key.hex` (mode 0600) — outside the artifact database, never in ctx.db, never sent to the client. Only the privileged handlers (piiEncrypt / piiDecrypt / piiEmailIndex) touch the key; actions declare those contracts. Encrypted columns: registrations.name, email, phone, faith_affiliation, hear_about, custom_answers (migration 0011 adds `pii_encrypted` + `email_hash`).
- **Email lookups without plaintext**: `email_hash` is an HMAC-SHA256 blind index of the normalized email under a key derived from the same key file, so lookupByEmail / lookupMyRegistrations / person-history match by index and never store or query the raw address. Pre-encryption rows are lazily re-encrypted (and indexed) on first read (`migratePlaintextRegs`).
- Staff emails on admin/gatekeeper lists and approver addresses are organizational contact data (needed to send approval requests and match sign-ins) and remain unencrypted; the encryption requirement covers attendee personal data.

## Admin reports & CSV export (admin-only)
- Correction (parent-relayed): gatekeepers do NOT get reports. Gatekeepers only check people in; the check-in data they record feeds admin reports. Reports/exports are admin-only and org-scoped.
- `attendanceReport` (per event): counts + checked-in list (with times), unused passes (approved, never checked in), pending, denied, revoked — built from registrations/checked_in_at recorded by gatekeeper/admin door scans.
- `personHistory`: cross-event history for one person within the admin's organization, by exact email (blind index) or partial name match.
- `exportContactsCsv`: admin-only CSV (name, email, phone, status, event, date, pass code, checked-in time, plus one column per question label) for one event or across all of the organization's events; the client downloads it as a .csv file for mailing-list use.

## Trusted participants (auto-approval)
- Follow-up spec (parent-relayed): admins can mark a participant as trusted (by email/Google ID); a trusted person's registrations are automatically approved on submission — pass issued immediately, no approver step. Admins view/add/remove trusted participants and can see which registrations were auto-approved.
- Storage: `trusted_participants` (migration 0012) — org_id, email stored AES-256-GCM-encrypted like all attendee PII, email_hash blind index for matching, optional google_id, display name.
- Flow: `register` / `registerGroup` check each attendee against the event organization's trusted list (email blind index; Google ID for the Google-linked submitter). A match goes through the shared `applyApprovalDecision` with decidedVia "Trusted participant — auto-approved", so the pass code is issued at once and no approval-request emails are created for that attendee. The register response reports per-attendee status/code/autoApproved; the success screen calls out instant approvals with their pass codes.
- Removal semantics (confirmed by a later follow-up): removing someone from the trusted list affects only future registrations — passes already issued stay valid; cancelling one is the separate Revoke action on the registration card. The admin Trusted panel states this in its copy and in the remove confirmation.

## New-event notifications (admin's choice at creation)
- Follow-up spec (parent-relayed): when an admin creates an event, offer the option to notify people that a new event is open — the organization's mailing/distribution list or trusted participants, with event details and the registration link. It is a choice at event-creation time (send or not, and who gets it), never automatic.
- Implementation: the admin event form (create only) has an "Announce this new event" selector (Don't send / Trusted participants / Mailing-distribution list / Both). On create, the client calls `sendEventNotification`, which resolves recipients server-side from the organization's own data only: trusted participants (decrypted from the trusted list) and/or mailing-list contacts — registrations whose answers include a Yes to a question whose label mentions "mailing" or "distribution" (covers each org's mailing-list question and, via the legacy column, CBI's Security Committee distribution list opt-in). The message carries the event title/date/time/location/description and the app's registration link (passed from the client, same pattern as approval links). Sends are logged in `event_notifications` (migration 0013: audience, recipient count, subject — recipient addresses are not stored in the log since they're attendee PII) and shown in a Notification history block; each existing event also has a "Notify…" control to send later. Consistent with the prototype's mail posture, the notification is composed and logged with its exact recipients and body shown to the admin, rather than emailed for real.

- Group contact (migration 0015): a group submission can route all approval emails and passes to one contact address (`contact_email`, encrypted + blind-indexed). Approvals and pass codes stay per-person. The contact finds the whole group's passes via the contact-email index in My Pass.

Approving a member reuses a sibling's code; `verifyCode` returns all members on the code and the door checks each person in individually (`checkInById`); revocation stays per person.

## Apple + email sign-in, email verification
- Sign in with Apple: Apple JS + server verification of Apple's ID token against Apple's JWKS (iss/aud/exp); the Services ID lives in `app_settings` (`apple_client_id`) like the Google client ID, with in-app setup steps and a labeled simulated fallback until configured. Identity id is `apple:<sub>`.
- Email-code sign-in: `email_signin_codes` (migration 0017) stores only the SHA-256 hash of the 6-digit code (10 minutes, single use). Identity id is `email:<address>` — the same identity a password account produces, so all methods link to the same person and roles by email/ID.
- Email verification (migration 0017): `email_verifications` tracks per-address verification globally. Registering with an unverified address creates a magic-link token (7 days); clicking it (`?verify-email=`) verifies once — future registrations with that address skip re-validation. Signing in with Google/Apple/email-code also marks the address verified. Admins see verification status per registration and can resend.

## Hidden events (added Nov 9, 2026)

Verbatim ask: "an organization can mark an event hidden — it does not display on the public calendar and is not searchable. The only way attendees can access it to register is through the direct event URL the organization sends them. Hidden events still work normally for registration, approval, and check-in once reached via that link."

- **Data**: `events.visibility` (`public` | `hidden`, default `public`; migration 0041), carried through the event structure args (create/update/series) and copied by duplicate/series-from-event.
- **Invisibility**: hidden events are excluded from the public `listEvents` (admins with includeAll still see them), from `searchEvents`, and from the subscribe-able iCal feed. They never appear on the public calendar, the embed, or attendee search results.
- **The link is the key**: `getEventForLink` returns one published event (public or hidden) by org + event id for the direct URL; `RegisterView` fetches and merges it when a deep-linked event isn't in the public list, so registration, approval, passes, and door check-in then work exactly as for any event. Drafts are not returned by the link fetch.
- **Client**: a Visibility select in the admin event form (with the link-only explanation), a "🙈 Hidden — link only" badge on admin event rows, and a note beside the event's direct link that it is the only way in.

## Undo for destructive actions

Destructive actions confirm in plain language what will happen and offer a 5-minute undo: revoking a pass (restores via `restoreMyRegistration` using the server-side `prev_status`, migration 0043), deleting a registration (restores via `restoreRegistrationSnapshot` from a snapshot captured before deletion), cancelling an event (restores its previous status), removing a trusted participant (re-adds them), and an attendee cancelling their own registration (`cancelMyRegistration` / `restoreMyRegistration` in My Events). ## Event cancellation/deletion notices and event-change notification

Cancelling or deleting an event asks how to notify: an announcement message shared with the cancellation notice, or quietly (plain notice only). ## Platform guidelines enforcement

Events are screened on create, edit, series creation, and publish (`screenEventGuidelines`, model-based, conservative: only the event's own purpose violating a named guideline flags — Illegal activity, Violence or dangerous activity, Weapons or explosives, Illicit drugs, Hate or extremist content, Fraud or scams, Sexual services, Self-harm, Other serious safety concern; education/prevention/support/safety-training content does not flag). This sits alongside the existing offensive-content moderation hold for registration fields.

## Service health, resilience, and the maintenance screen

`health_checks` and `service_incidents` (migration 0046). `getHealth` is the public probe (app + database + response time; every call is recorded); `getServiceStatus` tells the client whether to show the maintenance screen. `runHealthMonitor` (scheduled every 5 minutes, also runnable from the console) records a probe and enforces the outage policy: down for more than 5 minutes opens an outage incident — an automatic restart is requested and recorded in the incident, maintenance mode turns on for visitors, and an alert text is sent; a later successful probe closes the incident and texts the recovery. Three consecutive checks over the slow threshold open a "slow" incident with the same alerting. While maintenance is on, the app shows Gate, the mascot, with a reassuring "down for maintenance, back shortly" screen (platform owners can bypass to reach the console). The platform console's Service health panel shows status, uptime over recorded checks, average/p95 response times, recent checks, the incident log (including restart requests and whether the alert text was sent), a manual maintenance switch, and the alert configuration. The alert phone number and Twilio credentials (account SID, sending number, auth token) are configured in that panel and stored as platform settings — nothing is hard-coded; the token is never returned to the client (set/not-set only, SID masked to last 4). SMS sending runs through the `sendSms` privileged contract, which calls Twilio's Messages API (`https://api.twilio.com/2010-04-01/Accounts/<sid>/Messages.json`). Honest scope note: the artifact records the restart request and drives the maintenance screen; the actual process restart is performed by the hosting platform in response, and a fully down service cannot send its own text — the monitor and the owner's external polling of `getHealth` are the detection path, and the incident records whether the text was sent or why not.

### Passkeys, auth sessions, and server-side authorization (migration 0061)
- Tables: `passkey_credentials` (credential id, identity id, encrypted email + blind index, SPKI public key + algorithm, signature counter, transports, label — PUBLIC KEY ONLY; no password or shared secret is ever stored), `passkey_challenges` (single-use, 5-minute, purpose register/auth, rpId), `auth_sessions` (SHA-256 hash of a random 32-byte token — the token itself is never stored; method, 10-minute freshness window, 12-hour validity, revocation).
- A passkey is tied to the person's email in Approved Guest and to the unified identity that email already signs in as (`email:<address>`, Google sub, or `apple:<sub>`) — no Google or Microsoft account is involved at any point. Credentials are discoverable (resident), so cross-device sign-in via the platform's QR ("use a different device") hybrid transport works; the credential lives wherever the person chooses (iCloud Keychain, Windows Hello, an Android phone, 1Password/Bitwarden/Dashlane, a YubiKey).
- Bootstrap rule: `beginPasskeyRegistration` requires a valid verified session for the same identity/email — nobody can attach a passkey to an address they haven't proven they control. Google/Apple/email-code/password sign-ins all mint a session on success. Attestation accepts `fmt: "none"`; assertions verify ECDSA P-256/SHA-256 against the stored SPKI with the server challenge checked inside clientDataJSON and the signature counter tracked.
- Sign-in options are now passkey (first, recommended), Google, Apple, email code/magic link, and password; the email code/magic link stays as the fallback for anyone who can't or won't use a passkey. Registration without an account is unchanged — attendees register with just an email address.
- Authorization: every action already re-checks roles server-side per organization (owner/admin/registrar/greeter/attendee); `checkAuthorization` reports the server's view (roles, canManageUsers, hasPasskey, passkeyRequired, session validity/freshness) for the client to render from. Sensitive actions — approvals (`setApproval`), revocations (`revokeAttendance`), contact exports (`exportContactsCsv`), role invites (`createRoleInvite`), door-mode settings (`updateEventCheckinSettings`), geofence settings (`updateEventGeofenceSettings`), billing (`updateSubscription`, `addPaymentMethod`, `cancelSubscription`), passkey removal, passkey policy, and feature-flag changes — call `assertSensitiveAuth`: when the account has a live session (or presents a token), the token must be valid AND fresh (10 minutes). Accounts with no session at all (prototype simulated sign-in, or direct calls carrying only the provider-verified identity) fall back to the server-side role check alone; once they sign in through a verified flow, freshness is enforced. The client passes `sessionToken` on its requester/admin argument objects and offers one-tap passkey re-authentication in Sign-in & security when the session goes stale.
- Per-organization passkey policy (`app_settings` key `passkey_policy_<orgId>`, `{ requiredForStaff, requiredRoles }`, default off): owners can require passkeys for chosen staff roles (owner/admin/gatekeeper/registrant; requirement on + empty list = all staff roles). `checkAuthorization` reports `passkeyRequired` so affected members are prompted to add one. Attendees are never affected. Managed in Admin → Settings → Passkey policy; personal passkey management (list/add/remove, public-key fingerprint, session freshness) lives in My Events → Sign-in & security.

## Email-code sign-in hardening (Nov 11, 2026)
- Reported failure: email-code sign-in for a Gmail address failed with a "couldn't be confirmed" message; re-entering the SAME code as instructed also failed. ROOT CAUSE (found in `verifyEmailSignInCode`): the code row was DELETED before the fallible completion steps (role reconciliation, email-verified marking, session minting — privileged crypto + DB writes). Any failure in those steps, a lost success response, or a double-submit race burned the code permanently: every retry with the same correct code hit "No sign-in code was requested for that email" and could never succeed, even though the UI copy promised the same code would work. The 10-minute expiry compounded it.
- Fix (server, migration 0066 adds `email_signin_codes.used_at`): the code is consumed by marking `used_at` only AFTER all completion steps succeed — a failed attempt never burns it. A code consumed within the last 15 minutes REPLAYS: re-entering the same code mints a fresh session for the same identity instead of erroring (covers lost responses and double submits). Wrong code, expired, none-on-file, and already-used are distinct plain errors. Code validity lengthened 10 → 30 minutes (request copy and email body updated).
- Fix (client): `EmailSignInPanel` auto-retries the confirmation up to 3 times on non-verdict (connection) failures with a visible "confirming again automatically" status — verdict errors (wrong/expired/none/used) are shown plainly and never retried blindly; if retries run out, the message says plainly it was a connection problem, the code is still valid, and no new code is needed. The typed code is never cleared on failure.
- Sign-in primacy: the sign-in modal now groups passkey / Google / Apple under "⚡ One tap — the fastest way in"; the email-code and password panels moved behind a collapsed "Use an email code or password instead" fallback toggle.
